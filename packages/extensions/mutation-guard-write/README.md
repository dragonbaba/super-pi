# Mutation Guard: Edit and Write

Pi extension that overrides the built-in `edit` and `write` execution layers without adding a tool or slash command.

## Edit policy

- Every model receives one public `edit` tool whose provider-facing JSON Schema has a single `type: object` root and no union combinator. It advertises both preferred snapshot-line fields and guarded exact `oldText` fields as optional operation properties; execution immediately validates the complete payload against exactly one strict internal mode before permission handling or mutation, so mixed and incomplete calls fail closed. No second edit tool is exposed. Exact mode remains available whenever a read cannot issue a snapshot, including unsupported encodings, files above the compact ceiling, and other fail-closed cases.
- Successful stable text `read` calls rewrite each editable row as `LINE#ID|content`, append a session-only 128-bit opaque snapshot ID, and report the exact editable range. `ID` is a four-hex content check copied with the line number; it improves anchor accuracy but is not the security capability. A capability is minted only when one stable capture reproduces the displayed native read output exactly; images, invalid UTF-8, NUL, lone-CR, oversized, unstable, or mismatched reads do not qualify.
- Snapshot storage uses a schema-v2 `full | compact` receipt union and one LRU charged by resident bytes. Files up to 2 MiB use full immutable byte receipts. Larger ordinary text files up to 32 MiB, and JS/TS-family files up to 4 MiB, use a compact receipt produced by one 64 KiB streaming pass that hashes the whole file while retaining only the exact native 50 KiB/2000-line display window, adjacent boundaries, and absolute byte/EOL metadata under a 128 KiB resident cap. Compact execution rereads the current file, requires the original identity and whole-file SHA-256, edits only retained visible lines by stored byte offsets, preserves untouched bytes, and rechecks identity/hash immediately before atomic replacement.
- One call applies at most 20 non-overlapping `replace`, `delete`, `insert_before`, or `insert_after` operations to one existing file. Each operation copies exact `start` and optional `end` `LINE#ID` anchors from read output and supplies replacement content as `newLines: string[]`; every element is one physical line, so callers never manage boundary newlines. Anchor parsing accepts only the bare ID or known single-line display wrappers (`LINE#ID|content` and `>>> LINE#ID|content`, with outer whitespace); it never searches prose, normalizes lowercase IDs, or interprets body text. A mismatched ID may report one unique `Did you mean LINE#ID?` found strictly inside the visible window, but the call still fails and never remaps automatically. All anchors are interpreted against the immutable captured version and must remain within lines actually shown to the model. Exact duplicate operations are deduplicated, fully copied line prefixes are stripped conservatively, and copied surviving boundary lines are rejected with corrective guidance.
- Before any `.js`, `.jsx`, `.mjs`, `.cjs`, `.ts`, `.tsx`, `.mts`, or `.cts` snapshot mutation, the lazy syntax gate compares TypeScript parser diagnostics and rejects only newly introduced diagnostics. Existing diagnostics may remain; non-JavaScript/TypeScript text pays no parser-load cost.
- Successful snapshot edits return a real display diff, unified patch, and first changed line generated from the immutable before/after text; full before/after buffers are not returned in public details.
- Commit runs inside Pi's per-file mutation queue, reuses the central one-call protected-path approval and cumulative mutation budget, generates display diff and patch before mutation, verifies identity plus full SHA-256 before staging and again immediately before commit, writes one same-directory exclusive temporary file, syncs it, atomically replaces the target, and verifies readback. External writers that ignore Pi's queue can still race after the last verification on filesystems without shared locking; the staged replacement prevents Pi itself from leaving an in-place short write.
- The exact target file must have a successful text `read` from a prior tool turn, or a bounded prior mutation snapshot for that same file whose on-disk SHA-256 exactly matched the successful edit/write result. Evidence never crosses files or parallel sibling calls. Against the authoritative queued snapshot, a unique `oldText` may be accepted when it falls just outside the observed range; wholly unread files remain blocked.
- Successful targeted offset/limit reads are retained as bounded line-range evidence; truncated and image reads are rejected. A native read text block may be followed only by recognized bounded guardrail annotations (`Input repair`, `TLG`, or false-success markers), which are excluded from evidence; arbitrary extra content remains fail-closed. This preserves offset-repaired reads across `/reload` without trusting annotation text as file content. The in-memory LRU retains at most 32 file identities and 16 ranges per file; evicted evidence requires a new read.
- If `oldText` is repeated, it must appear in prior range evidence; a targeted read covering exactly one occurrence selects it automatically. Otherwise, optional `expectedLine` must identify exactly one occurrence by its 1-indexed start line. When `oldText` is unique, exact content identity is authoritative and a stale `expectedLine` left behind by earlier line-shifting edits is ignored.
- Selection and bounded unique-context expansion happen inside Pi's per-file mutation queue against the same snapshot used by the native edit implementation.
- Pi's native exact/fuzzy matching, uniqueness, overlap checks, line-ending preservation, diff, and patch behavior remain authoritative after disambiguation in the exact branch; snapshot mode performs no fuzzy matching.
- One call is limited to 20 replacements and 256 KiB total old/new text scope; occurrence scans, retained evidence, expanded context, and disambiguated snapshots are also bounded.
- Across one turn, successful/in-flight edit and write calls share a cumulative budget of 24 calls, 16 files, 100 replacements, and 1 MiB. Failed non-mutating reservations are released; partial mutations remain charged. The next structured `turn_start` resets the budget.
- Successful results report replacement count, estimated scope, and `stateChanged: true` without mutating the original tool-call arguments recorded in the transcript.
- The former `edit-recovery` behavior is integrated here: after a safe edit failure, bounded inspection scans only the implicated replacement and returns concise category, relevant locations, and Retry text instead of internal JSON plus every edit diagnostic. `already_applied` remains conservative: each old block is absent, each replacement is unique and ordered, and every replacement has exact-line or stable context evidence.
- A write failure is inspected against the pre-edit hash and reported as `EDIT_FAILED` or `PARTIAL_MUTATION`.

## Write policy

- New files use exclusive creation (`wx`) so a concurrently appearing target is not overwritten.
- Overwriting an existing text file requires a successful complete `read` from a prior tool turn. A read starting at line 1 with an explicit `limit` is promoted to complete only when the returned UTF-8 byte length and SHA-256 exactly match the current regular file; this recognizes a bounded read that actually reached EOF without trusting display annotations.
- Inside Pi's per-file mutation queue, current SHA-256 must equal the exact full text returned by that read.
- Genuine partial reads, truncated reads, images, same-turn evidence, stale evidence, and pre-tree-navigation full-read evidence are rejected.
- After a successful guarded edit/write result, the extension reads the file back from disk and stores its bounded SHA-256 evidence only when it exactly matches that result's expected hash. Snapshots up to 256 KiB also become full-file edit-range evidence for a later turn; larger files remain hash-only and still require a targeted read before edit. This permits later edit/overwrite chains without redundant reads while preserving stale-state detection; same-turn use, missing hashes, failed readback, or concurrent post-success changes invalidate evidence.
- On `session_start` (including `/reload`) and `session_tree`, the in-memory store is cleared and reconstructed from a 512-entry result window on the active branch, plus at most 128 preceding entries used only to pair a boundary result with its assistant tool call. Only paired successful `read`, `edit`, and `write` receipts qualify; mutation receipts are read back and SHA-256 verified against disk, and a newer malformed or stale successful mutation receipt invalidates older evidence for that exact path. Restored evidence is always older than the next tool turn.
- Edit and write use the same canonical prospective-path protection as high-risk Bash. `resource-lifecycle-guard` is the sole Session permission controller and attaches a non-enumerable, exact one-call approval after any required TUI/RPC decision. This guard never opens a second dialog: it consumes that approval, then independently revalidates the canonical target and violation set immediately before mutation. Missing, stale, mismatched, non-UI, or unverifiable approvals fail closed. A rejected or unconfirmed protected path cannot be reclassified as `already_applied` success.

## Structured-mutation-only ledger

Successful exact edits, snapshot edits, overwrite writes, and exclusive creates now emit a schema-v1 structured mutation receipt directly in their authoritative Session `toolResult.details`. A receipt contains only `mutationReceiptVersion`, operation, bounded target, `stateChanged`, preimage SHA-256 when a preimage exists, postimage SHA-256, and bounded replacement/create metadata. Exact edit exposes the preimage hash already computed by its stale-state gate; no additional hash, read, write, listener, closure, or custom Session entry is added.

`collectStructuredMutationReceipts()` derives a read-only ledger from at most the latest 512 Session entries. It accepts only complete versioned successful `edit`/`write` receipts, requires matching operation and valid hashes, rejects unsafe targets and malformed/create-with-preimage shapes, and never copies tool content, patch/diff bodies, purpose text, or original arguments. The Session tool result remains the sole state source; there is no second ledger file, custom-entry stream, database, lifecycle owner, or resume reconciliation problem.

Bash, scripts, delete/move commands, LSP fixes, and subagents are intentionally excluded. Their actual write set cannot be proven from the structured mutation receipt contract, so including them would create a falsely complete ledger. Existing permission audits and tool-error telemetry remain separate and must not be presented as file mutation receipts.

Reproduce the bounded scan benchmark with `npm run benchmark:ledger`. The committed 10,000-entry workload scans only the latest 512 entries and emits 32 receipts over 9×1,000 iterations: median 0.00687 ms, p80 0.00711 ms, output hash `bdaa9c48487a5a5ae2828e3dfdeae202e99c50bd6f3ac803957e81cd0a1173dc`. The collector is on-demand and is not called by ordinary turns.

## Scope

This is the sole global `edit` override; it exposes a provider-independent union of preferred snapshot-line and guarded exact-replacement schemas. The former `edit-recovery` extension is retired outside auto-discovery. This guard covers built-in single-file `edit` and `write`; the three-mode Session permission state, additional workspaces, rejection feedback, dialogs, audits, and structured Bash protection remain centralized in `resource-lifecycle-guard`. Dedicated delete/move tools, shadow workspaces, and multi-file transactions are intentionally deferred with evidence in `FOLLOW_UP_GAPS.md`.
