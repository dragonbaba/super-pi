# 一、执行原则

1. **按可独立验收的阶段或子阶段组织改动，PR 串行推进**。同一时间只推进一个待合并 PR；当前 PR 审查及 CI 通过、合并并清理远端和本地分支后，才能开启下一 PR。详细流程见 1.2；本次文档修订不表示代码实施已经开始。
2. **已确认的决策不再重新讨论**（D1–D8 已确认，D9 暂缓）。实施中发现决策无法落地时，停止该阶段并记录原因，交用户决定。
3. **测试适量且有效**：每条关键实现路径使用代表用例与正常对照，优先复用已有测试，不做无依据的组合矩阵、不堆叠镜像实现的测试。先运行最小相关检查；只有新的改动、失败或未解决疑点才扩大或重复本地测试。必要回归、性能契约检查和 CI 不因此省略。测试维护要求见 1.3。
4. **所有代码严格遵守性能文档**：实施前阅读 [性能文档入口](performance/README.md)、[热路径分配契约](performance/hot-path-allocation-contract.md) 及所改模块的专项规范，覆盖闭包、热路径、常量与正则处理、分配和生命周期。普通代码也须遵守适用规范，不得因阶段标为非热路径而免除检查；具体要求见 1.1。
5. **验证文件**：每次运行产生的夹具、探针临时副本和原始输出放在 `.task-tmp/<task-id>-<unique-id>/`；子进程的 `TMP`/`TEMP`/`TMPDIR` 设为该目录并验证实际生效。清理前，将可复现方法保留为仓库回归测试、基准脚本或文档中的最小复现代码，记录基线、命令、关键结果与限制。不能仅保留指向待清理临时脚本的路径和命令；资源登记与清理遵守 `AGENTS.md`。
6. **完成证据**：每个阶段或子阶段单独记录实现状态、验收状态、实际测试命令与结果、稳定复现入口及未验证事项；PR 编号、提交与合并信息仅在实际发生后填写。必要真实验证未完成时标为“实现完成、待验收”，不写成该阶段完成。
7. **威胁模型**：防止模型误操作，不是对抗性安全边界。转义、拼接、`eval` 等绕过写法记入 #161，不扩展解析器。
8. **阶段内验证**：每个阶段完成前执行自身必要的真实 VM、真实子进程或交互验证；阶段 F 负责已完成范围的集中回归与性能测量，不替代前置验收，也不因某个待决策分支而阻塞无关阶段。
9. **保持实现简洁**：按已证实的问题与明确需求修复，避免不必要的兜底、静默重试、重复校验、兼容层及抽象结构。保留确有必要的权限、身份、完整性和资源释放约束；不能以减少防御性代码为由删除这些保证。
10. **最终离线构建**：全部修复任务完成后，在包含全部合并结果的本地基线上运行 `npm run build:offline`，成功后记录提交、命令、退出状态和产物检查结果；失败则返回修复与 PR 审查流程，不把任务标为全部完成。当前仅编辑计划，无须为文档改动提前执行整仓构建。

## 1.1 性能规范的执行要求

- 所有新增、迁移和修改代码均检查适用规范；热路径审查覆盖生产者到释放边界的完整调用链及已有 helper，不只看新 diff。
- 普通高频路径按契约禁止逐事件/逐帧创建内联闭包、Promise 回调或 executor、定时器回调，以及循环内 `bind(this)`。使用模块函数或所属生命周期仅创建一次的实例回调；低频例外必须具体到函数并有证据，不能整文件或整类豁免。
- 固定限额、标记、正则和可复用不变数据统一定义并避免在循环或热路径反复构造。提升为模块常量时核对可变状态、重入与生命周期；不得把实例状态或可变 scratch 变成共享全局，也不以常量化代替配置语义。
- 按契约检查 Promise、AbortController、包装对象、临时数组、字符串复制与物化、缓存容量和引用释放。对象池仅在满足契约全部准入条件时使用，不作为默认优化或兜底结构。
- 每个涉及热路径的 PR 提供对应源码/AST 不变式、相关分配基准、确定性计数、分配证据和正常完成/失败/取消/销毁的释放证据；耗时数字不能单独证明合规。只运行对应路径需要的检查，不无依据地重复全部基准。

## 1.2 每个 PR 的审查与合并流程

1. 从上一个 PR 已合并且分支已清理的基线开始本 PR，明确问题、依赖、验收项及性能规范，完成必要本地验证后首次提交、推送并发起审查。
2. 首次提交后等待 reviewer 完成审查；若未触发审查，通过 PR 评论中的 `@codex` 手动请求。没有反馈或等待超时不等于审查通过。
3. 对每条反馈核对源码、复现条件和证据。问题确实存在时修复；同时判断是否暴露本计划的设计、依赖、范围或验收遗漏，并同步修正相应条目。不成立的反馈记录理由和证据并澄清，不能机械照改，也不能未经核实直接忽略。
4. 修复后运行最小相关验证，提交并推送修复；**每次修复提交后在 PR 评论中通过 `@codex` 手动触发复审**，等待最新提交的审查结果。继续处理新反馈，直到没有剩余有效问题或未澄清争议。
5. 确认 reviewer 已审查当前最新提交、反馈均已处理，且该提交的全部 CI 检查通过，才合并。不能用旧提交的审查/CI 结果替代，也不能通过关闭检查、跳过有效用例或忽略失败达到“通过”。
6. 确认 PR 已合并后，按该 PR 的实际 head 分支身份清理**远端分支与本地分支**；删除前检查没有额外未交付提交、工作树改动或其他任务占用，不丢弃用户变更。记录两个分支均已清理，才允许开启下一 PR；清理受阻则保留准确状态并先解决。

以上是本计划实施时的前置流程。各阶段的“完成记录”须同时记录审查反馈处理、计划补漏、手动 `@codex` 复审、最新提交的 CI、合并及远端/本地分支清理结果；未发生的步骤保持待填。

## 1.3 测试数量与 CI 成本维护

- 每个 PR 在所触及模块内检查是否存在过期、重复或已被更高层有效回归覆盖的测试；在阶段收尾再次汇总，及时清理确已失去独立验证价值的用例及失效测试入口。
- 清理时说明删除或合并的原因、仍覆盖该风险的测试与 CI 执行影响。有效的权限、数据完整性、生命周期和性能回归不得仅因耗时而删除；不能用清理掩盖失败。
- 不为可逆低影响改动或与实现逐行同构的逻辑堆测试；新增测试应对应可观察行为、已复现问题或明确验收要求。保留稳定复现方法，临时运行输出按 1.4 管理。
- 本地相关检查通过后，只有新变更、失败或未解决问题才重复或扩大测试；CI 按配置完整运行并全部通过。无新增证据时不连续重跑相同全集，不让冗余测试持续增加 CI 成本。

## 1.4 临时资源与最终交付

临时文件统一放入现有 `AGENTS.md` 约定的 `.task-tmp/<task-id>-<unique-id>/`，本计划先以此落实用户所称的任务临时目录；若用户明确指定另一目录，再统一调整，不能混用两套位置。所有测试、基准、构建子进程在启动前设置 `TMP/TEMP/TMPDIR`，验证其实际使用该任务根；登记文件、目录和进程身份。

清理前保留简洁可复现证据，释放进程及句柄，核对绝对目标和链接边界，仅清理本任务登记的资源。清理受阻时记录准确路径、原因和剩余清单，不切换机制绕过，不宣称清理成功。仓库构建的正式产物仍按构建脚本的约定输出；临时中间文件、日志和分析数据必须在任务临时目录内。

最终交付记录须包含：已完成与明确延期的范围、各 PR 最新审查/CI 与分支清理状态、稳定验收证据、最后一次本地离线构建的基线及结果、临时资源清理结果。仍有已确认修复任务、必要验证或离线构建未完成时，不宣称全部任务完成。
