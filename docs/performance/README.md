# Performance benchmarks

Phase 0 benchmarks are offline, deterministic, and write JSON only to standard output. They never require provider credentials and do not modify source files.

The permanent [hot-path allocation contract](hot-path-allocation-contract.md) defines the production call chains, closure/Promise/object/array/string limits, lifecycle evidence, and object-pool admission gates for Phase 4C and all later hot-path work in Phases 5–8. Its source invariants and allocation fixtures are regression baselines, not one-time Phase 4C evidence.

Run the default corpus with Node's TypeScript stripping. `--silent` keeps redirected output valid JSON, and the explicit `npm run -- <script>` form works across the supported npm versions:

```text
npm run --silent -- bench:stream
npm run --silent -- bench:tool-progress
npm run --silent -- bench:tui-transcript
npm run --silent -- bench:tui-frame-allocations -- --fixture production-main --items 50000
npm run --silent -- bench:tui-frame-queue-allocations -- --frames 20000 --frame-kib 64
npm run --silent -- bench:tui-session-event-allocations -- --updates 100000 --warmup 10000
npm run --silent -- bench:tui-frame-queue
npm run --silent -- bench:prefix
npm run --silent -- bench:tool-output
npm run --silent -- bench:model-runtime
npm run --silent -- bench:model-runtime:warm
```

Every result uses `BenchmarkResult` schema version 1 and records the commit, Node version, OS/architecture, CPU, memory, terminal dimensions, fixture version, warm-up/measurement counts, p50/p95/p99, min/max, coefficient of variation, heap observations, and benchmark-specific string/boolean observations such as content hashes. Defaults are 5 warm-up and 20 measured runs; local smoke checks may use `--warmup 1 --runs 3`. Shared CI checks schema and deterministic structural counters rather than machine-specific millisecond thresholds.

Larger variants are generated in memory instead of committed as blobs:

```text
npm run --silent -- bench:tui-transcript -- --items 50000 --width 200 --height 60
npm run --silent -- bench:tui-retained-lifecycle -- --items 50000 --cycles 5
npm run --silent -- bench:tool-output -- --mebibytes 10
npm run --silent -- bench:prefix -- --context-kib 1024
```

The TUI transcript benchmark constructs the production `UserMessageComponent` and `AssistantMessageComponent` tree inside the retained transcript container, primes it through `TuiMainScreen`, and applies deterministic synchronous terminal backpressure to every measured update. `RetainedContainer.children` continues to contain the original components; session-local sidecar records own cached lines and never replace child identity. It records root, completed-item, active-item, overlay, generated/visible-line, target-height/block probes, viewport item visits, composed/copied lines, full-history fallbacks, cursor-scanned lines, terminal diff/byte, retained-cache, pending-render-request, and terminal-frame-queue counters. `pendingRenderRequestHighWaterMark` is the TUI's coalesced latest render intent. `terminalFrameQueueHighWaterMark`, `terminalActiveWriteHighWaterMark`, and `terminalPendingFrameHighWaterMark` describe the actual bounded terminal-frame queue and are recorded when a write starts, not when a stale frame is replaced. A completed item retains only its latest width and presentation-version render; active items remain uncached until completion freezes their logical version. Invalidation propagates into the original component, including image/cell-dimension caches. A completed tool's deferred image conversion or custom renderer invalidation advances only that sidecar's visual generation, leaving the frozen logical version and unrelated completed items untouched. The default slow sink rate is 16 KiB/s; change it explicitly with `--terminal-bytes-per-second`. Pass `--cpu-only` to disable simulated sink delay, or `--full-history` to retain the Phase 4A full-history composition path as an in-process control.

Phase 4B adds per-item height metadata, an O(1) cached document height, and a 256-item block-height index. Bottom-following frames locate the target from the final non-zero block and walk backward only far enough to cover the viewport; trailing zero-height records therefore cost at most the block count plus one 256-item block. Historical Fullscreen scrolling locates the containing block before scanning item heights. Main Screen performs one full initial replay (and a full replay at resize/Kitty safety boundaries) so terminal scrollback remains available, then diffs only its visible absolute-line window. Each indexed document exposes an opaque mutation generation plus bounded attribution: only an explicit tail append or a range rooted in the previous visible window can use the bounded path. Offscreen mutations, reorder/rebuild, presentation boundaries, stale attribution, and unknown changes replay the full document. Successful text-only windows preserve IDs for offscreen Kitty images until a later full replay deletes them. Fullscreen composes transcript and overlays separately. Cursor/IME scanning therefore receives viewport lines only. Line-range composition copies only intersecting lines—even from one ordinary or retained 100,000-line item—and carries a numeric Kitty boundary/header observation separately when cropping must start inside an image. Measured dirty lines are single-query scratch: dirtying, width changes, early returns, successful composition, and exceptions all clear `preparedLines`. Dynamic plain transcript children must call `invalidateViewportChild()` when their height can change; retained version/visual invalidation does this automatically. Direct `children.splice()` insertion or replacement must call `notifyChildrenChanged()`; permanent removal continues to use `removeChild()` or `clear()` so sidecars and height records are released.

On 2026-08-27, Windows x64, Node 26.4.0, i7-14700KF, 120×40, CPU-only closeout runs with 100 warmups and 1,000 measured active updates produced 5,000-item p50/p95 of 0.0245/0.0352 ms and 50,000-item p50/p95 of 0.0246/0.0383 ms. Both sizes performed exactly 17 target-height probes, zero block probes, 17 viewport item visits, 40 composed/copied lines, one active render, zero completed renders, and zero full-history fallbacks. Isolated roughly 3.4 ms process/GC outliers make the aggregate coefficient of variation noisy, so p95 and deterministic structural counters remain the useful CPU evidence. With the deterministic 16 KiB/s sink (5 warmups, 20 measurements), 5,000 items measured 10.269/10.337 ms p50/p95 and 50,000 measured 10.273/10.337 ms; both wrote 167 bytes. Controlled-GC lifecycle runs (3 cycles, 1 warmup, 3 measurements) used 20 height blocks for 5,000 items and 196 for 50,000; `clear()` reduced retained items, cached lines, indexed items, and height blocks to zero. Resize peaks were 66,565,992 and 328,502,624 bytes, and final controlled-GC heap slopes were 8,176 and 21,020 bytes/cycle respectively. These noisy slopes are trend evidence, while the zeroed structural counters are the portable lifecycle gates.

The retained lifecycle variant requires `--expose-gc` (included in its npm script). It records numeric cache ownership before clear, verifies every retained/cache count reaches zero after clear, and samples controlled-GC heap after repeated create/render/resize/clear cycles. Heap slope is evidence for trend review, not a pass/fail assertion from one noisy process sample.

Known Phase 4B boundaries remain intentional after Phase 4C: the first Main Screen replay, width resize, non-Termux height resize, upward content shrink, and Kitty safety boundaries still use the full renderer; arbitrary historical lookup scans forward through 256-item height blocks, while a stable bottom frame performs zero block probes; a 50,000-item width remeasurement can produce a high transient heap peak (328,502,624 bytes in the closeout run above); and extension-provided dynamic transcript children must call `invalidateViewportChild()` after any height-changing mutation.

Phase 4C adds an instance-local bounded terminal-frame queue. It owns at most one active write and one pending latest frame string. Replacing pending output immediately drops the old string reference; there is no Promise tail, unbounded frame array, object pool, or cross-session cache. Main and Alt renderers defer generation of a new relative diff while a prior frame is active, retaining one render intent instead; this prevents a newer diff from being based on an intermediate frame that never reached the terminal. All content and cursor writes emitted by one `doRender()` are composed into one atomic frame before enqueue, so cursor metadata cannot replace its content. Explicit queue clients still receive latest-value replacement. `flushTerminalFrames()` loops until both the queue and any frame published in the settled-before-cleanup microtask window are idle, then materializes any deferred latest render. TUI stop, Main/Alt mode switches, normal shutdown, suspend, external-editor handoff, and fatal/error cleanup use this boundary. `AgentSession.subscribe(..., { criticalAgentEnd: true })` is the explicit final-run contract: only these listeners are awaited at `agent_end`; ordinary pending listeners do not block, critical rejection is isolated, and message/tool updates retain their non-awaited path. The complete critical lane has one 30-second safety deadline, after which later critical listeners are still invoked but are not awaited.

The Phase 4C numeric gates are `activeWrite <= 1`, `pendingLatestFrame <= 1`, queue HWM `<= 2`, at most one shared deferred per busy cycle, zero normal-frame Promises, `AbortController`s, wrapper objects, and application full-size copies, plus at most one final full-size frame materialization. These gates apply unchanged to later hot-path work; Phase 5 tool-output processing, Phase 6 Evidence Ledger lookup, Phase 7 primitive reuse, and Phase 8 soak/release work must run the relevant source invariant and allocation baseline rather than treating the Phase 4C result as historical documentation only.

`Terminal.write()` is the awaited control-sequence API and every asynchronous result must be awaited or passed through the bounded control observer. All terminal-owned unawaited controls—including paste, keyboard, cursor, clear, title, and progress sequences—use the instance `frameOutput`, one stable callback, and the same bounded outstanding-write ownership; `ProcessTerminal` contains no direct `process.stdout.write()` bypass. The rendered-frame API is callback-driven: one stable `setFrameWriteCompletionListener()` is registered per TUI, and `writeFrame(data, generation)` carries only the frame string and a numeric generation. `ProcessTerminal` reports completion only after both the real Writable callback succeeds and either `write()` returned true or a false return was followed by `drain`; callback-before-drain and drain-before-callback are equivalent. Physical-start bytes are counted only after `Writable.write()` returns without throwing. A process-terminal-owned `error` observer contains an error event emitted after callback failure, while per-write drain/close listeners are always removed. Normal frames create no Promise, `AbortController`, signal/options wrapper, `Set`, or `Map`. `flush()` lazily shares one deferred per busy-to-idle cycle. Ordinary frame writes have no absolute deadline: a measured 128 KiB write at 16 KiB/s completed normally after roughly eight seconds. The independent stop/fatal/suspend/mode-switch lifecycle boundary defaults to 5,000 ms. Frame and awaited-control deadline errors carry an exact recoverable identity that the same TUI may clear on its next `start()`; callback/EPIPE/EIO/close failures remain permanent and supersede a recoverable timeout. A canceled frame retains the physical writer slot and its callback/drain ownership until it settles; one replacement frame may wait in fixed primitive slots and cannot start or consume orphan events early. Final `dispose()` makes the terminal non-reusable and drops logical listeners immediately, but removes its sole stream error observer only after every frame, awaited control, and unawaited control write settles. Ordinary `stop()` preserves the terminal for mode switch, suspend, or external-editor resume.

The Phase 4C production queue benchmark uses `TuiBase`, an atomic `doRender()` frame, a gated asynchronous terminal, and controlled GC. On 2026-08-28, Windows x64, Node 26.4.0, i7-14700KF, 120×40, 5 warmups, and 20 measurements, 100,000 render requests measured 7.3054/7.7959 ms p50/p95. It made exactly two `doRender()` calls, generated two frame strings, wrote two unique frames, retained one pending render intent, reached maximum active write one and frame-queue HWM one, and ended with zero active writes/bytes. The final sentinel was `frame-99999-of-99999:` and SHA-256 was `bdb9144c20814fd20e44475c378bcde45b85110114954f472fc0c55b3f3cf6a0`; controlled-GC delta was 7,608 bytes. The 100,000-request × 64 KiB run measured 7.1136/8.0659 ms p50/p95 with the same 2/2/2/1 structural counts, two unique frames, final sentinel match, SHA-256 `5e5be363f77142aeea5b5c0e09ac2c712d457f2303afc3d02a43ae7434f53b80`, and 154,152-byte controlled-GC delta. Both runs recorded zero full-size copies, frame Promises, frame `AbortController`s, and frame wrapper objects. Heap deltas are noisy trend evidence; render/frame counts and final identity are the portable gates.

The direct queue benchmark gates the first of 10,000 unique 64 KiB frames. It records active/pending `1/1`, queue HWM 2, exactly two writer calls, 9,998 replacements, final SHA-256 `b884dbabfd3ff3c5a117714ba25c4e8834ca05509424f0438c365ea03b77d9c6`, and post-flush active/pending/writer references `0/0/0`. Controlled-GC delta was 2,168 bytes, so no replaced-frame string chain remained reachable.

The real transcript full-replay benchmark explains the earlier 50,000-item resize peak rather than treating one heap sample as a queue leak. In the final callback closeout rerun, 5,000 items emitted a 1,486,692-byte first width replay and grew from 45,358,208 to 78,431,688 bytes; controlled GC after flush, lifecycle abort, and clear returned 46,819,480, 45,955,968, and 24,671,168 bytes. At 50,000 items, the first replay was 14,866,692 bytes and heap grew from 258,654,008 to 400,737,208 bytes; controlled GC after flush, abort, and clear returned 267,921,416, 258,683,832, and 49,334,624 bytes. Both sizes had one active terminal-frame reference, zero queue-pending frame references, and one numeric render intent while gated; flush and abort ended at `0/0/0` with no terminal frame reference. Each complete width/abort sequence generated exactly three final frames, zero full-size copies, and zero frame Promise/controller/wrapper objects; maximum frame sizes were 1,966,692 and 19,666,692 bytes. A same-candidate retained-lifecycle rerun with no terminal queue reached 414,245,080 bytes during the same 120→96→144 width sequence and then cleared every structural count to zero. Therefore the earlier 327,010,400 vs 435,438,800 values were noisy cross-run resize peaks, not a 108 MB queue-owned delta. The transient increase is dominated by full-history line composition, width-specific retained renders, and the active serialized frame—not an active+pending string chain. At 16 KiB/s the first 5,000/50,000 replay projects to 90.7/907.4 seconds, which is why normal write completion cannot share the five-second lifecycle deadline.

The Phase 4C allocation gate uses two independent inspector-sampling fixtures on Windows x64, Node 26.4.0, i7-14700KF. `queue-only-prebuilt-frame` reuses one 64 KiB input for 1,000 warmups and 20,000 measured writes; it sampled 104.69 B/frame, with `performance.now()` and benchmark bookkeeping accounting for the leading sites, zero minor GC, one major GC taking 1.60 ms, and a 250,120-byte controlled-GC delta. Queue `start` and `finish` sampled 14,040 and 1,120 bytes total across 20,000 writes. It recorded zero queue-created closures, frame Promises, frame `AbortController`s, wrapper objects, frame-string materializations, and full-size copies, then finished with active/pending bytes `0/0`. The render-plus-queue fixture used the real seven-root Main tree and real Alt `ScrollView`/`VStack` tree for 20,000 active-only frames. After extracting Main's remaining local render closures and debug serialization into stable instance methods, Main sampled 7,069.34/7,343.09 B/frame at 5,000/50,000 items with p50/p95 0.0203/0.0283 and 0.0216/0.0469 ms; Alt sampled 36,523.15/36,523.29 B/frame with p50/p95 0.0811/0.2041 and 0.0814/0.1127 ms. Inspector/GC timing outliers make single-run p95 noisy, while allocation totals and deterministic counters stayed flat. Each group generated exactly one final frame per measured render, zero full-size copies, zero frame Promises/controllers/wrappers, and ended with active/pending frame bytes `0/0`. The flat 5,000→50,000 results preserve Phase 4B's history-size independence; Alt remains the documented layout-allocation backlog rather than Phase 4C queue work.

A separate 16 MiB direct-frame run generated two fixture strings without prebuilding an array. At the gate, queue active/pending were `1/1`, each 16,777,216 bytes; heap was 42,850,952 bytes. After flush, queue and writer references and active/pending byte counts were all zero, controlled-GC heap returned from 9,249,368 to 9,253,544 bytes, the queue had materialized/copied no full-size strings, and the final frame hash was `8e95808ec5d112f5c1c813a3319d5ec663bf016c43226bfcef8b0bb0ebfa6205`.

Phase 4B regression controls remained item-count independent after atomic frame composition. At 120×40, 5 warmups, and 20 measurements, CPU-only 5,000/50,000-item p50/p95 were 0.0454/0.0942 ms and 0.0391/0.0873 ms. The 16 KiB/s controls were 10.6551/10.7410 ms and 10.6536/10.7298 ms. Both sizes retained 17 viewport visits/probes, 40 copied lines, one active render, zero completed renders/fallbacks, one atomic terminal write, and queue HWM one.

The Phase 4B allocation closeout uses `tui-frame-allocations.ts` with inspector heap sampling (1,024-byte interval), GC `PerformanceObserver` entries, and controlled GC before and after each active-only frame run. Its `direct-main` fixture isolates one retained transcript; `production-main` uses the seven-root production shape with header and loaded-resource children inside the document; `production-alt` uses the real `ScrollView` plus nested `VStack` dock layout. All fixtures use a CPU-only no-op terminal. The benchmark reports the top 20 sampled allocation sites, transcript viewport result arrays and copied lines, mutation-ring writes, aggregate and per-child plain render counts, and deterministic viewport work. `viewportLineArraysPerFrame` counts transcript viewport result arrays; outer layout arrays remain visible in the inspector site report rather than being inferred from source. The mutation ring writes once per attributed mutation, not inherently once per terminal frame; this benchmark advances exactly one active item on each measured frame, which is why its fixture reports one mutation write per frame.

The prefix benchmark builds every resource ordering per sample and records the canonical manifest SHA-256, hash-set SHA-256, unique hash count, and drift count. Its fixture identity includes the context size and `prefix-manifest-v1`, preventing comparisons against the older raw-prefix drift harness.

The stream and tool-progress benchmarks use the coalesced observer lane by default. Add `--legacy-delivery` to measure the compatibility `subscribe()` lane, which intentionally awaits and delivers every requested update:

```text
npm run --silent -- bench:stream -- --legacy-delivery
npm run --silent -- bench:tool-progress -- --legacy-delivery
```

Delivery mode is part of each stream/tool-progress fixture identity, so latest and legacy results cannot be compared accidentally. To measure assistant snapshot cost under a provider-like 16 ms cadence, run the paced stream fixture (30 updates by default):

```text
npm run --silent -- bench:stream -- --paced-16ms
```

The cold model-runtime benchmark launches one independent child process per sample, including module loading and production offline runtime construction without credential refresh. The warm fixture constructs another runtime in the already-loaded benchmark process. Both verify `modelCount === profiledModelCount` and record provider/model counts. Use matching Phase 2 and Phase 3 worktrees on the same machine to enforce the Phase 3 cold and warm startup p95 regression budget of at most 5%.

Save baseline and candidate JSON outside the source tree (or under ignored `.artifacts/`) and compare them with:

```text
npm run --silent -- bench:compare -- baseline.json candidate.json
```

Comparison is rejected unless benchmark/fixture, Node version, platform, architecture, warm-up and measured run counts, CPU identity/core count, total memory, terminal dimensions/type, Kitty mode, and exposed-GC mode match. Commit and measurement timestamp are expected to differ and are not comparability keys.
