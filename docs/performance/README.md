# Performance benchmarks

Phase 0 benchmarks are offline, deterministic, and write JSON only to standard output. They never require provider credentials and do not modify source files.

The permanent [hot-path allocation contract](hot-path-allocation-contract.md) defines the production call chains, closure/Promise/object/array/string limits, lifecycle evidence, and object-pool admission gates for Phase 4C and all later hot-path work in Phases 5–8. Its source invariants and allocation fixtures are regression baselines, not one-time Phase 4C evidence.

Run the default corpus with Node's TypeScript stripping. `--silent` keeps redirected output valid JSON, and the explicit `npm run -- <script>` form works across the supported npm versions:

Every result uses `BenchmarkResult` schema version 1 and records the commit, Node version, OS/architecture, CPU, memory, terminal dimensions, fixture version, warm-up/measurement counts, p50/p95/p99, min/max, coefficient of variation, heap observations, and benchmark-specific string/boolean observations such as content hashes. Defaults are 5 warm-up and 20 measured runs; local smoke checks may use `--warmup 1 --runs 3`. The TUI transcript benchmark constructs the production `UserMessageComponent` and `AssistantMessageComponent` tree inside the retained transcript container, primes it through `TuiMainScreen`, and applies deterministic synchronous terminal backpressure to every measured update. `RetainedContainer.children` continues to contain the original components; session-local sidecar records own cached lines and never replace child identity. It records root, completed-item, active-item, overlay, generated/visible-line, target-height/block probes, viewport item visits, composed/copied lines, full-history fallbacks, cursor-scanned lines, terminal diff/byte, retained-cache, pending-render-request, and terminal-frame-queue counters. `pendingRenderRequestHighWaterMark` is the TUI's coalesced latest render intent. `terminalFrameQueueHighWaterMark`, `terminalActiveWriteHighWaterMark`, and `terminalPendingFrameHighWaterMark` describe the actual bounded terminal-frame queue and are recorded when a write starts, not when a stale frame is replaced. A completed item retains only its latest width and presentation-version render; active items remain uncached until completion freezes their logical version. Invalidation propagates into the original component, including image/cell-dimension caches. A completed tool's deferred image conversion or custom renderer invalidation advances only that sidecar's visual generation, leaving the frozen logical version and unrelated completed items untouched. The default slow sink rate is 16 KiB/s; change it explicitly with `--terminal-bytes-per-second`. Pass `--cpu-only` to disable simulated sink delay, or `--full-history` to retain the Phase 4A full-history composition path as an in-process control.

Phase 4B adds per-item height metadata, an O(1) cached document height, and a 256-item block-height index. Bottom-following frames locate the target from the final non-zero block and walk backward only far enough to cover the viewport; trailing zero-height records therefore cost at most the block count plus one 256-item block. Historical Fullscreen scrolling locates the containing block before scanning item heights. Main Screen performs one full initial replay (and a full replay at resize/Kitty safety boundaries) so terminal scrollback remains available, then diffs only its visible absolute-line window. Each indexed document exposes an opaque mutation generation plus bounded attribution: only an explicit tail append or a range rooted in the previous visible window can use the bounded path. Offscreen mutations, reorder/rebuild, presentation boundaries, stale attribution, and unknown changes replay the full document. Successful text-only windows preserve IDs for offscreen Kitty images until a later full replay deletes them. Fullscreen composes transcript and overlays separately. Cursor/IME scanning therefore receives viewport lines only. Line-range composition copies only intersecting lines—even from one ordinary or retained 100,000-line item—and carries a numeric Kitty boundary/header observation separately when cropping must start inside an image. Measured dirty lines are single-query scratch: dirtying, width changes, early returns, successful composition, and exceptions all clear `preparedLines`. Dynamic plain transcript children must call `invalidateViewportChild()` when their height can change; retained version/visual invalidation does this automatically. Direct `children.splice()` insertion or replacement must call `notifyChildrenChanged()`; permanent removal continues to use `removeChild()` or `clear()` so sidecars and height records are released.

On 2026-08-27, Windows x64, Node 26.4.0, i7-14700KF, 120×40, CPU-only closeout runs with 100 warmups and 1,000 measured active updates produced 5,000-item p50/p95 of 0.0245/0.0352 ms and 50,000-item p50/p95 of 0.0246/0.0383 ms. Both sizes performed exactly 17 target-height probes, zero block probes, 17 viewport item visits, 40 composed/copied lines, one active render, zero completed renders, and zero full-history fallbacks. Isolated roughly 3.4 ms process/GC outliers make the aggregate coefficient of variation noisy, so p95 and deterministic structural counters remain the useful CPU evidence. With the deterministic 16 KiB/s sink (5 warmups, 20 measurements), 5,000 items measured 10.269/10.337 ms p50/p95 and 50,000 measured 10.273/10.337 ms; both wrote 167 bytes. Controlled-GC lifecycle runs (3 cycles, 1 warmup, 3 measurements) used 20 height blocks for 5,000 items and 196 for 50,000; `clear()` reduced retained items, cached lines, indexed items, and height blocks to zero. Resize peaks were 66,565,992 and 328,502,624 bytes, and final controlled-GC heap slopes were 8,176 and 21,020 bytes/cycle respectively. These noisy slopes are trend evidence, while the zeroed structural counters are the portable lifecycle gates.

The retained lifecycle variant requires `--expose-gc` (included in its npm script). It records numeric cache ownership before clear, verifies every retained/cache count reaches zero after clear, and samples controlled-GC heap after repeated create/render/resize/clear cycles. Heap slope is evidence for trend review, not a pass/fail assertion from one noisy process sample.

Known Phase 4B boundaries remain intentional after Phase 4C: the first Main Screen replay, width resize, non-Termux height resize, upward content shrink, and Kitty safety boundaries still use the full renderer; arbitrary historical lookup scans forward through 256-item height blocks, while a stable bottom frame performs zero block probes; a 50,000-item width remeasurement can produce a high transient heap peak (328,502,624 bytes in the closeout run above); and extension-provided dynamic transcript children must call `invalidateViewportChild()` after any height-changing mutation.

Phase 4C adds an instance-local bounded terminal-frame queue. It owns at most one active write and one pending latest frame string. Replacing pending output immediately drops the old string reference; there is no Promise tail, unbounded frame array, object pool, or cross-session cache. Main and Alt renderers defer generation of a new relative diff while a prior frame is active, retaining one numeric render intent instead; this prevents a newer diff from being based on an intermediate frame that never reached the terminal. After a lifecycle-canceled OS write becomes an orphan, `ProcessTerminal` retains no replacement frame string: it exposes physical availability and one stable ready callback. A resumed TUI therefore coalesces B→C before materialization, while direct queue clients retain only one replaceable latest frame. All content and cursor writes emitted by one `doRender()` are composed into one atomic frame before enqueue, so cursor metadata cannot replace its content. `flushTerminalFrames()` loops until the writer is available, the queue is idle, and any frame published in the settled-before-cleanup microtask window has completed. TUI stop, Main/Alt mode switches, normal shutdown, suspend, external-editor handoff, and fatal/error cleanup use this boundary. `AgentSession.subscribe(..., { criticalAgentEnd: true })` is the explicit final-run contract: only these listeners are awaited at `agent_end`; ordinary pending listeners do not block, critical rejection is isolated, and message/tool updates retain their non-awaited path. The complete critical lane has one 30-second safety deadline, after which later critical listeners are still invoked but are not awaited.

The Phase 4C numeric gates are `activeWrite <= 1`, `pendingLatestFrame <= 1`, queue HWM `<= 2`, at most one shared deferred per busy cycle, zero normal-frame Promises, `AbortController`s, wrapper objects, and application full-size copies, plus at most one final full-size frame materialization. These gates apply unchanged to later hot-path work; Phase 5 tool-output processing, Phase 6 Evidence Ledger lookup, Phase 7 primitive reuse, and Phase 8 soak/release work must run the relevant source invariant and allocation baseline rather than treating the Phase 4C result as historical documentation only.

`Terminal.write()` is the awaited control-sequence API and every asynchronous result must be awaited or passed through the bounded control observer. All terminal-owned unawaited controls—including paste, keyboard, cursor, clear, title, and progress sequences—use the instance `frameOutput`; `ProcessTerminal` contains no direct `process.stdout.write()` bypass. Recurring progress has a dedicated primitive lane with at most one in-flight keepalive and one pending clear intent, so a slow or never-settling callback cannot grow `controlWritesOutstanding`. `start()` is transactional, and `stop()` attempts every input/listener/raw-mode restore before reporting its first synchronous control error; `dispose()` completes permanent logical release even when stop reports an error. The rendered-frame API is callback-driven: stable completion, physical-start, and physical-ready listeners are registered per TUI, and `writeFrame(data, generation)` carries only the frame string and a numeric generation. `ProcessTerminal` reports completion only after both the real Writable callback succeeds and either `write()` returned true or a false return was followed by `drain`; callback-before-drain and drain-before-callback are equivalent. Physical-start bytes are counted only after `Writable.write()` returns without throwing. A process-terminal-owned `error` observer contains an error event emitted after callback failure, while per-write drain/close listeners are always removed. Normal frames create no Promise, `AbortController`, signal/options wrapper, `Set`, or `Map`. `flush()` lazily shares one deferred per busy-to-idle cycle. Ordinary frame writes have no absolute deadline: a measured 128 KiB write at 16 KiB/s completed normally after roughly eight seconds. The independent stop/fatal/suspend/mode-switch lifecycle boundary defaults to 5,000 ms. Frame and awaited-control deadline errors carry an exact recoverable identity that the same TUI may clear on its next `start()`; callback/EPIPE/EIO/close failures remain permanent and supersede a recoverable timeout. A canceled frame retains the physical writer slot and its callback/drain ownership until it settles; a resumed renderer keeps only a numeric intent, and direct queue clients keep one replaceable pending string. Final `dispose()` makes the terminal non-reusable and drops logical listeners immediately, but removes its sole stream error observer only after every frame, awaited control, and unawaited control write settles. Ordinary `stop()` preserves the terminal for mode switch, suspend, or external-editor resume.

Overlay composition is also part of the render hot path. It consumes the caller-owned per-frame line array in place, uses instance-local parallel scratch arrays instead of `filter`/`sort`/record wrappers, and clears all rendered-line references in `finally`. Terminal cell dimensions use one stable `const` object; `setCellDimensions(dims)` copies only `dims.widthPx` and `dims.heightPx` into that object, so get/set allocate nothing, object identity does not change, and no caller-owned object is retained.

The real transcript full-replay benchmark explains the earlier 50,000-item resize peak rather than treating one heap sample as a queue leak. ### Phase 4D-B1 Alt layout allocation closeout

The production Alt fixture is the real retained transcript, `ViewportContainer`, primary `ScrollView`, nested `VStack` dock, layout/paint pass, `TuiAltScreen.doRender()`, and bounded terminal-frame queue. The stable fixture changes one active retained item per frame; optional `--alt-control overlay|selection|cursor-ime|mixed` controls exercise real overlays, absolute-row selection, cursor/IME markers, ANSI, CJK, emoji, and combining marks. Kitty placement and cropping remain an independent golden safety control because image frames intentionally disable text-row reuse.

Phase 4D-B1 replaces the per-frame nested render-cache Maps and filtered stack arrays with one per-TUI synchronous `LayoutFrameScratch`. It retains at most two viewport-sized screen/row-cache buffers and bounded primitive layout ranges; it never crosses an await or crosses TUI instances. On the first extension-visible `visible(viewport)` call in a frame it creates exactly one fresh `{ width, height }` value and reuses that value only within the frame, so an extension may retain it without observing a later frame mutate it; frames without visibility callbacks allocate no viewport wrapper. Width/height changes invalidate row reuse. Reentrant rendering receives an isolated temporary scratch, exceptions clear child, line, index, row-cache, and screen references, and `stop()` drops every retained reference. Heights above 4,096 rows and transient layout ranges above 4,096 records are not retained. `LayoutFrame.lines` is a borrowed scratch-owned buffer: the current frame may compose it in place, but it must be consumed before the same scratch renders again.

Stable full-width text rows reuse their already padded painted strings; image, partial-width, scrollbar, and cropped-Kitty rows are deliberately uncacheable. The row cache retains at most 65,536 code units per source/painted pair and 524,288 code units across both scratch buffers; source and painted strings both count, and oversized ANSI/OSC rows are rejected by code-unit length without UTF-8 rescanning or copying. A 1 MiB zero-width OSC row and a 10 MiB plain row retain zero row-cache strings. The cumulative-cap fixture retains 521,964 code units and rejects the remaining 76 rows. The two screen buffers deliberately preserve the immediately previous raw frame for Alt's identity comparison; an old oversized screen is released when that buffer is next reused, and `clear()`/stop/dispose reach zero references. The final Alt normalization screen is instance-owned and swapped with the previous screen, eliminating the old full-viewport `slice()` while preserving current-layout ownership. No object pool, Proxy, global cache, frame Promise, or full-size frame copy was introduced.

Render lookup keeps the direct-array path through 24 records. Larger layouts lazily activate one instance-owned `Map<Component, recordIndex>` with primitive previous-index chains for the uncommon same-component/multiple-width case. The index is cleared after every complete or aborted frame, discarded with backing arrays above 4,096 records, and never writes metadata onto components or uses a global `WeakMap`. The old 64-leaf fixture required 4,096 probes; the bounded implementation records 256/444/1,020/3,324 probes for 16/64/256/1,024 unique leaves. The regular nine-node production tree never activates the index. Dynamic instrumentation reports lookup probes, record count, index activations, retained source/painted code units, maximum row code units, and size rejections. Zero nested-cache Maps and zero lookup-wrapper objects are explicitly source invariants rather than fabricated runtime counters.

### Phase 4D-B2 Alt overlay and selection allocation closeout

Phase 4D-B2 leaves `LayoutFrameScratch`, the retained viewport/index, row-cache limits, screen-buffer swap, and terminal frame queue unchanged. Its production fixture traverses retained transcript → `ScrollView`/`VStack` Alt layout → overlay or absolute-row selection composition → cursor/IME and line reset → terminal frame queue. Controls cover one and multiple overlays, overlay movement/z-order/focus behavior, single- and multi-line selection, selection across the viewport, ANSI, CJK, emoji, combining marks, cursor/IME, and a mixed two-overlay plus eleven-row selection frame. Kitty remains an independent safety control because image rows intentionally take the existing uncached fallback.

Overlay composition now owns one pair of per-TUI, fixed-shape result scratch records for ANSI segment extraction and bounded slicing. The records contain only primitive counters and current line strings, are never extension-visible, and clear every string in `finally`, including render failure. Selection resolution uses fixed primitive/reference fields and paints each selected row in one terminal-sequence/grapheme pass instead of allocating translated point/range wrappers and running three independent slice passes. Printable ASCII text runs use direct indexed loops; CJK, emoji, combining sequences, wide characters, and other non-ASCII text continue through `Intl.Segmenter`. Public compatibility helpers keep their existing return shapes, while the Alt hot path calls the allocation-sensitive `...Into` and primitive-boundary forms. No object pool, cross-session scratch, `Map`, `Set`, Promise, controller, full-screen copy, or additional frame string is introduced.

### Phase 4D-B3 Editor layout allocation closeout

The B3 Plan Gate compared five separate production boundaries before selecting an implementation target. A real retained Alt tree rendered `Editor` on every active transcript frame. Mouse hit testing sampled about 797 B/event, selection auto-scroll about 404 B/tick, and a forced Kitty image-redraw control about 10.9 KiB/redraw frame; those paths are event-bound, limited to the 20 Hz edge-drag interval, or image-only safety work. Direct `HStack`/`VStack.render()` sampled about 92.3 KiB/call but is bypassed by the production Alt `LAYOUT_NODE` path, which the dynamic test records as zero direct stack renders. The real Editor path sampled about 91.3 KiB/frame, and `Editor.layoutText()` alone accounted for roughly 1.576 GiB of the 1.826 GiB sampled over 20,000 frames. It was therefore the only candidate combining per-frame frequency, a dominant allocation site, and a credible improvement above 15%; B3 does not modify the other four candidates.

`Editor` now retains one bounded, instance-local layout checkpoint. ### Phase 4D-A0 TUI core allocation coverage

`ProcessTerminal.drainInput()` is callback-driven rather than an async polling loop. The first caller creates a generation-scoped cycle and fixes its finite, non-negative absolute and idle deadlines using a monotonic clock; concurrent callers share that Promise and cannot extend, shorten, or reschedule the cycle. Zero is valid, and the absolute maximum wins when the idle duration is longer. One cycle owns one shared Promise, at most one concurrently active timer, one resolver/rejector pair, one previous-handler slot, and stable instance callbacks for Promise capture, stdin data, and timer expiry. The timer high-water mark is not a total-allocation count: input near an idle boundary can expire one handle and reschedule another within the same cycle. The stable timer receives the numeric generation through `setTimeout`; a canceled cycle's late timer cannot settle a replacement cycle or restore an old input handler. A data event updates only `lastDataTime`; it does not replace the timer, create a callback, or create a Promise. The real-`EventEmitter` 100,000-event lifecycle benchmark reports dynamic high-water counts of one Promise, concurrently active timer, listener, resolver, and rejector, with zero identity changes and every reference cleared after the cycle. Its explicit reschedule scenario reports `timerHandlesCreatedPerCycle=2` and `timerReschedulesPerCycle=1`; these are reported separately from `maximumTimers=1`. Separate AST invariants report zero Promise and inline timer-callback allocations per input event. Completion, stop, dispose, and synchronous terminal-control failure all use the same generation-checked cleanup; synchronous failure rejects the shared Promise instead of escaping. Startup stdin-buffer data/paste callbacks and the keyboard-fragment timer are likewise stable instance callbacks. The remaining inline Promise/callback in `Terminal.write(data)` is an explicit low-frequency awaited-control boundary whose concurrent calls require independent resolve/reject ownership; it is not used by normal frame, input-event, or progress-tick delivery.

OSC 11 background queries use one logical wave Promise, one first-caller deadline, one resolver, one generation-owned timer, and at most one physical request. The timer callback receives the active numeric generation; a stale timeout from a completed wave cannot clear or settle its replacement. A second caller in the same wave shares the first caller's deadline. Because OSC 11 responses carry no request identifier, a timed-out physical request leaves one boolean tombstone, and one newer logical wave waits for that stale reply before sending its own physical request. If the follower also reaches its deadline, the TUI caches OSC 11 as unsupported; later calls reuse one resolved result with no timer, resolver, or physical write. A late valid response is still consumed, clears the unsupported cache, and permits a fresh query. The 10,000-call no-response soak keeps active records, tombstones, timers, and resolvers at one, and final dispose clears all query references.

The public `Component.render()` contract does not impose one ownership model on cached and uncached components: ordinary callers treat returned arrays as read-only unless a narrower API grants mutation. `Container.render()` is that narrower API; it returns one fresh caller-owned outer array, and mutating it never mutates a child's cached lines. Nested base containers flatten through the module-level `renderContainerInto(container, width, target)` helper. The helper never dynamically dispatches a public-looking `renderInto` property, so a JavaScript extension with the same method name cannot collide. Inherited base renders flatten, overridden and foreign/cross-realm components naturally fall back to `render(width)`, and render errors propagate. This preserves the measured approximately 0.99% sampled allocation reduction without adding a copy on Markdown or RetainedItem cache hits.

Input cursor-right and backspace paths iterate grapheme segmentation without materializing the full iterator, and paste/key classification uses direct iteration rather than callback arrays; Unicode, CJK, emoji, and combining-mark tests retain the existing behavior. Default `RetainedItem`s share the module-level `getDefaultRetainedContext` callback and the same frozen context value instead of allocating an equivalent closure per item. Windows VT setup and modifier checks reuse one lazily loaded native helper across package, source, and executable candidate paths rather than rebuilding a candidate array on each lookup. Overlay focus hot methods use indexed loops and one fixed mutable restore record; overlay stack entries use one fixed-shape allocation without conditional spread and are deliberately not pooled because extension-visible handles can outlive `hide()`.

Production Alt removed the duplicate layout-line copy, empty flash render/slice, and no-Kitty prepared-result object, but remains dominated by `String.repeat`, Alt diff composition, `paintBox`, and `layoutComponent`. Layout box/rect/Map reuse was deliberately not added: those costs belong to the existing layout implementation, and this closeout does not introduce object pools. All six runs retained zero block probes, one mutation write, one transcript viewport array, and 32 or 40 copied visible lines per frame, so the allocation changes do not hide an item-count-dependent traversal.

Production Alt's approximately 36.5 KB sampled allocation per frame, two active renders per frame, and maximum three renders per plain child are recorded as a non-blocking follow-up boundary. They are not a Phase 4B correctness or scaling regression, and reducing them must not be conflated with Phase 4C terminal frame queue work.

Final Phase 4C transcript controls (100 warmups, 1,000 CPU-only measurements) measured 5,000-item p50/p95 of 0.0245/0.0356 ms and 50,000-item p50/p95 of 0.0239/0.0379 ms. With the 16 KiB/s sink (5 warmups, 20 measurements), they measured 10.6590/10.7378 ms and 10.6548/10.7139 ms respectively. Both sizes retained 17 visits/probes, 40 copied lines, one active render, zero completed renders, zero fallback, and one 173-byte atomic terminal frame. Controlled-GC lifecycle controls (3 cycles, 1 warmup, 3 measurements) recorded resize peaks of 65,869,864 and 414,245,080 bytes and final heap slopes of 10,064 and 12,868 bytes/cycle. These single-process resize peaks remain noisy trend observations, not queue allocation gates; the portable result is that the 50,000-item run held 50,000 index records and 196 blocks before clear, then reported zero retained items, cached lines, indexed items, and blocks after clear.

The prefix benchmark builds every resource ordering per sample and records the canonical manifest SHA-256, hash-set SHA-256, unique hash count, and drift count. Its fixture identity includes the context size and `prefix-manifest-v1`, preventing comparisons against the older raw-prefix drift harness.

The stream and tool-progress benchmarks use the coalesced observer lane by default. Add `--legacy-delivery` to measure the compatibility `subscribe()` lane, which intentionally awaits and delivers every requested update:

```text
npm run --silent -- bench:stream -- --legacy-delivery
npm run --silent -- bench:tool-progress -- --legacy-delivery
```

Delivery mode is part of each stream/tool-progress fixture identity, so latest and legacy results cannot be compared accidentally. To measure assistant snapshot cost under a provider-like 16 ms cadence, run the paced stream fixture (30 updates by default):

```text
npm run --silent -- bench:stream -- --paced-16ms
```

The cold model-runtime benchmark launches one independent child process per sample, including module loading and production offline runtime construction without credential refresh.
