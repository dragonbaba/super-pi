# Auto 风险筛选与会话排查

日期：2026-11-15。基线：`d9718ad8ced517e3e34a362b17152fb56e17f060`。仅离线检查历史记录和受控测试，没有重放实际会话工具、调用真实 provider 或修改用户项目。

## 结论与改动

Auto 原先沿用宿主机受限的询问范围，普通 shell/MCP 操作也会请求审查，原生工作区内文件修改反而可能直接放行。本轮将选择依据改为风险：工作区内普通读取、搜索、查询及常规构建/测试直接执行；原生文件变更、已识别的 shell 文件变更和 destructive MCP 声明触发审查。

不透明的 shell/MCP/自定义调用由主模型在执行前通过 `callTool(name, args, { review: true })` 标记风险。提示明确列出删除/覆盖、项目或应用状态变更、软件安装、系统设置、Git 历史改写及向外部发送私有数据。元数据通过 CodeMode → NestedToolDispatch → AgentSession → 权限 owner 传递，不进入底层工具参数；与 `allowFailure` 独立，不代表批准。没有新增脚本解析器或命令白名单；宿主无法识别的副作用依赖主模型遵守该约定，不能视为对抗性安全边界。

显式 deny/ask、已有允许规则、工作区边界和沙箱机制保留。普通工作区外读取仍由用户审批；工作区外删除/移动、显式 ask 和 `approval: "never"` 不由模型代答。审查未完成时回到持续等待的人工审批。拒绝熔断、当前会话/权限代次和完整参数绑定的单次重试继续生效。在已有的有界拒绝/重试记录仍保留该调用时，省掉 review 元数据也不会把完全相同的调用降为普通操作；用户允许重试后仍须审查。

历史 CodeMode 错误发生在工具文档已经完整返回之后：下一次请求自行指定非零 offset，却没有传回 revision，因而被续页校验拒绝，未执行子工具。提示现在展示 revision 参数，要求只按返回的续页指令继续；完整页面显式标记无需续读。保留原有定义版本检查，避免 MCP 更新后混读不同版本。此改动改善调用指导，不能保证模型永不发出无效请求。

## 缓存证据与边界

历史成功响应中有短间隔的大幅缓存回退：前次报告命中 85,632、115,712、145,152 token，约 23、20、62 秒后的对应响应分别报告 87,099、117,416、148,166 个未缓存输入 token、零缓存命中。较长暂停后的未命中和失败请求的全零 usage 单独排除，不能混作同一种现象。

历史会话没有持久化每次实际发送的前缀观察，无法确认上述请求的序列化前缀、缓存键、路由和 provider 缓存状态是否相同。其中一次零命中前存在工具目录激活，但仅凭历史逻辑消息不能证明实际请求前缀变化，也不能解释另外两次回退。结论仍是原因未确定，不能宣称已修复缓存失效。

当前 Auto 已走 `SupplementalSummaryScope`：强制 `cacheRetention: "none"`、SSE、关闭远端 compaction，并移除普通请求的 `onEffectiveDispatch` 写入。因此没有证据支持“Auto 审查覆盖了主请求前缀基线”的推断，本轮没有修改 provider 缓存实现。减少审查请求可省去对应模型请求的消耗，不能换算成已证明的主请求缓存改善。

## 分配与生命周期

审计调用链：CodeMode 全局 helper → invoke/runChild → NestedToolDispatch.callTool → AgentSession 的 beforeToolCall → 执行权限 owner → 已有扩展事件派发。新增数据为既有调用/事件对象的布尔字段及两个模块级冻结 options 对象；调用准备时读取元数据。风险延续复用既有拒绝/重试 owner 和完整参数指纹，不增加新缓存，非文件变更的同一指纹在拒绝检查与审查间复用。provider delta、工具 progress、渲染和终端帧更新路径未增加回调、Promise、AbortController 或包装对象；原有调度 Promise 和队列未增加。source invariants 与 CodeMode 热路径检查通过。

同一 Windows 机器、Node v26.13.0，以基线和候选交替运行三组 `codemode-dispatch` 等价工作负载。每次均完成 100 个 owner 生命周期、800 次调用，最大并发 4；1,100 个 owner/catalog/参数弱引用在关闭和受控 GC 后全部释放。基线调度源码取自上述基线提交，其他基准代码一致。
