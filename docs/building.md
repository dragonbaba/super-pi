# 本地构建

依赖已经安装时，在仓库根目录的 PowerShell 7 中执行：

```powershell
npm run build:offline
npm run superpi -- --offline --version
npm run superpi -- --offline --help
```

首次安装或锁文件变化后先运行 `npm ci`。构建输出位于各包的 `dist/`；删除 `.task-tmp` 不会删除这些产物。

`npm run build:offline` 就是正式本地离线构建入口。PowerShell 执行策略若拦截 npm 安装目录中的 `npm.ps1`，可以使用 npm 自带的 `npm.cmd`，不需改永久策略或另建仓库 `.cmd`/`.ps1` 构建脚本；这与在线 npm 包是否发布无关。

## 入口与行为

| 命令 | 行为 |
| --- | --- |
| `npm run build:offline` | 使用现有模型数据，自动为 npm 子构建启用离线模式，默认最多并行两个包 |
| `npm run build:offline -- --jobs 1` | 同一构建计划串行执行，便于诊断和对照 |
| `npm run build:offline -- --list` | 只显示包、构建脚本和依赖，不编译或刷新数据 |
| `npm run build` | 保留原在线构建语义，AI 包会先刷新模型数据，可能访问网络 |

`--jobs N` 接受 1–32 的整数；实际并发还受依赖关系和包数限制。默认值为 CPU 可用并行度与 2 的较小值。无需再写外层 `npm --offline`，原命令仍兼容。构建离线模式与 CLI 的 `--offline` 独立，均不意味着模型推理离线。

统一入口是 `scripts/build.mjs`。构建目标仍是原来的 12 个包；执行顺序来自这些包的 `dependencies`、`devDependencies` 和 `peerDependencies`。包必须等其依赖成功结束后才能开始，循环依赖或缺失构建脚本会在启动子进程前报错。各包继续负责自己的编译、资源复制、SQLite migration 和 MXC 运行时资源打包。

每次调用仍会构建全部目标，没有引入增量缓存或跳过产物检查的捷径。启动器也不会自动重建源码。更新源码后应显式构建，再检查 `--version` 和 `--help`。

## 失败、取消与输出

首次构建失败或取消后，入口不再启动新的包，等待已经启动的 npm 子进程退出后返回非零状态。取消时可能需要等待当前包完成。输出直接继承到终端，不在 JavaScript 中缓存或逐块处理；并行包的输出可能交错，`[build] START/END` 会标记包名、耗时和退出状态。需要连续查看单包输出时使用 `--jobs 1`。

## 退役与验证

根 `package.json` 中两条重复的 `cd ... && npm run ...` 串行长命令已由统一入口替代。在线与离线模式共用一份目标集合和调度逻辑，包内仍在使用的编译、模型数据校验、资源复制和沙箱打包步骤继续由原脚本负责。

回归测试覆盖依赖顺序、开发/peer 依赖、并发上限、循环拒绝、离线参数继承、失败与取消后的进程收尾。CI 仍执行现有的构建和完整测试流程。

2026-11-04 在同一 Windows 主机、Node 26.13.0 下，对同一入口进行了三次串行和三次双并发构建，顺序为 `1, 2, 2, 1, 1, 2`。测量使用预热后的文件系统环境，所有 12 个包都实际执行，没有省略构建步骤：

| 并发数 | 三次耗时（ms） | 中位数（ms） |
| --- | --- | --- |
| 1 | 10823、11122、11037 | 11037 |
| 2 | 7446、7422、7536 | 7446 |

该对照中位数下降约 32.5%。六次构建后的 2,848 个产物文件逐文件 SHA-256 指纹完全一致，同时运行的包构建数峰值分别为 1 和 2。数据属于此机器和此版本的验收结果，不是其他硬件上的耗时保证；此前一次独立完整构建的 26.6 秒不参与这个百分比计算。

精确计数、哈希和验证命令见[验收证据](evidence/build-pipeline-2026-11-04.json)。构建调度发生在显式构建命令生命周期内，没有修改模型流、工具输出、终端渲染或其他运行时热路径。
