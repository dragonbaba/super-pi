# 二、新需求：宿主机模式删除项目外路径须询问

## 2.1 需求

> 宿主机模式下，删除非当前项目的路径的内容时，需要询问，得到同意后才能删除，不能一律跳过或一律否决。

已确认的范围（D1–D6，2026-11-06）：

- 宿主机删除确认规则只针对“全部读写（宿主机）”模式。前两档在 VM 内执行，不把宿主原工作区及其他用户目录直接映射为可写；映射还包含只读工具链与任务专属可写交换目录，不能笼统说“所有项目外路径不可达”。D7/D8 属于另行确认的沙箱行为调整。
- “当前项目”= 主工作目录 + `/add-dir` 显式添加的目录。
- “删除”包括：删除文件或目录、`move` 移走源文件、递归删除命令，以及等价的 shell/脚本删除。
- 普通工作区外删除的目标：**询问一次，用户同意才执行**；不允许静默放行，也不允许不问就拒绝。关键路径以及 D3、D6 的受保护目标直接拒绝，不能通过这次询问放行。
- 覆盖或编辑工作区外已有文件采用 D5：不执行该操作，立即暂停当前整轮任务并告知用户，等待用户下一步指令。该规则不替代普通工作区外删除的询问流程。
- 模型通过工具修改 agent 自身目录采用 D6 的专门规则：修改先询问，删除直接拒绝并通知。程序自身正常保存配置和会话不受这条工具规则影响。

## 2.2 当前行为（证据范围见 4.1）

宿主机模式下，原生策略在未命中显式规则时默认放行：

- `packages/coding-agent/src/core/execution-policy.ts:178`：`selected ?? fallback ?? (this.mode !== undefined || ... ? "allow" : "ask")`，只要有三档模式，默认结果就是 `allow`。
- 同文件 `paths()`：宿主机模式的变更只放过 `workspace_escape` 一种违规，所以项目外的 delete/move 通过路径检查后直接允许。
- 旧的删除防护（resource-lifecycle-guard）在原生模式下整个跳过：`packages/extensions/resource-lifecycle-guard/index.ts:149` `if (getSessionFiles(pi)?.hasNativeAuthorization) return;`。这与本轮确认的“工作区外普通删除必须询问”不符。旧审计引用的 10-17/10-18 历史决策未在本次定位到原始记录（它们来自审计助手的会话记忆，不在仓库内），本轮以 2.6 的明确回答为准。

逐入口现状：

| 入口 | 宿主机模式删除项目外路径 | 依据 |
| --- | --- | --- |
| `delete` 工具 | 直接执行 | `execution-policy.ts` `paths()` + 默认 allow |
| `move` 工具（源在项目外） | 直接执行 | 同上 |

| 浏览器 / chrome-devtools | 不是本次原生文件删除分析的覆盖保证 | 普通浏览器操作不等于删除本地文件；经 MCP 或不透明程序提供的文件能力仍属于已声明边界 |

| --- | --- | --- | --- | --- |
| Claude Code | `acceptEdits` 模式只对工作目录和 `additionalDirectories` 内路径自动批准 `rm`/`mv` 等，“Paths outside that scope”仍提示 | “critical paths”（文件系统根、顶层目录、HOME 含 8.3 短名、Windows 盘符根及其顶层目录、工作目录及其父目录）的 `rm`/`rmdir`：任何 allow 规则或 hook 都不能批准。默认模式询问；连 `bypassPermissions` 在终端也询问。无法可靠解析时提示“Dangerous rm operation not ruled out”。PowerShell `Remove-Item` 删系统路径或裸 `*` 通配：所有模式直接拒绝；`-Recurse` 删工作目录或其父目录：按模式询问 | `auto`/`bypass` 下有 2 分钟倒计时，超时**仅拒绝这一次**；连续 3 次超时后本轮自动拒绝，用户发新消息即重置。非终端（-p、SDK）默认拒绝 | 官方文档 |

| Cline | Auto Approve 的项目外编辑需启用基础编辑开关及“Edit all files” | 命令是否需批准由模型给出的 `requires_approval` 决定，无固定名单 | YOLO 自动批准文件、命令及 MCP 等调用 | 官方文档 |
| Gemini CLI | 默认策略的写入工具与 shell 请求批准，策略可改变结果；引擎提供 allow/ask_user/deny | 本轮未确认统一的项目外路径专门规则 | `yolo` 自动批准；不能把默认模式表述成所有配置下必问 | 官方文档；原 concepts 链接已失效，改引 policy-engine |
| Cursor | 有 “File-Deletion Protection”（删除需批准）和 “External-File Protection”（项目外创建/修改/删除需批准）两个开关 | 用户报告经 PowerShell、`rmdir /s /q` 绕过两个开关并删光整盘 | — | 非官方 |

共同点：

1. **工作区是多家产品在默认或指定模式中的审批边界**；不能推导出所有权限模式都强制审批项目外操作。Cursor 仍仅为非官方资料，不作为实施依据。
2. **灾难性目标单独处理，不受 allow 规则影响**（Claude Code 最完整：根、HOME、盘符根直接拒绝或强制询问）。
3. **命令解析不是安全隔离保证**：Claude Code 官方文档明确说明检查可能漏命令；Cursor 只有用户绕过报告，不能写成“各家官方均已承认”的共同事实。
4. **超时只拒绝本次，不会永久拉黑**（Claude Code）。
5. **没有交互通道时，需要人工批准的调用不能据此自动获得批准**。具体自动允许/拒绝行为由各家模式与规则决定；“不记成用户拒绝”是本项目的明确设计要求，不当作已核实的各产品统一实现。

**MCP 审批复核补充（2026-11-06）**：

- Codex 支持 MCP 服务器级 `default_tools_approval_mode` 和工具级 `approval_mode`，其中 `writes` 会对未标为只读的工具询问。因此既不能说“所有 MCP 都不询问”，也不能把 app/connector 的规则无条件推广到所有 MCP 客户端配置。[官方 MCP 文档](https://learn.chatgpt.com/docs/extend/mcp)
- Codex [App Server 文档](https://learn.chatgpt.com/docs/app-server#mcp-tool-call-approvals-apps) 说破坏性注解触发审批，即使同时有更低权限的注解；[审批与安全文档](https://learn.chatgpt.com/docs/agent-approvals-security) 则写只读注解优先。两处对冲突注解的优先级描述不一致，本轮未验证客户端实际实现，不把这项优先级写成统一保证。
- Claude Code 支持按 MCP 服务器或工具设置 allow/ask/deny；组织要求询问的 connector，以及标记 `requiresUserInteraction` 的工具，另有必须交互的规则。未在本轮查阅的官方页面中确认“只要 `destructiveHint: true` 就在所有模式强制询问”的统一规则。[官方权限文档](https://code.claude.com/docs/en/permissions#mcp)、[权限模式文档](https://code.claude.com/docs/en/permission-modes)
- 本项目 D9 已由用户决定暂缓：本轮不新增基于 `destructiveHint` 的强制询问，也不改变现有 MCP 授权规则。

### 目标分类与结果

| 类 | 目标 | 建议结果 | 说明 |
| --- | --- | --- | --- |
| A | 项目内普通路径 | 允许（不变） | 宿主机模式的意义所在 |
| B | 项目根本身、项目内 `.git`/`.sp` 受保护范围 | **拒绝，并明确反馈模型与用户**（D3 已确认） | 保持原生文件工具现有保护范围，补齐 shell；`.git`/`.sp` 保护包含其内部路径 |

目标判定先统一规范化：同步入口使用 `realpathSync.native`，异步入口沿用 `fs.promises.realpath`（与 B1 的修复保持一致）；已存在的父目录解析目录联接与符号链接，不存在的部分按 `canonicalizeProspectivePath` 补齐。必须区分“删除链接本身”和“经链接访问并删除目标”：不能把前者无条件解析成链接指向的目标后套用后者的判断，具体边界见 2.5。

### 询问的语义

| 项 | 建议 |
| --- | --- |
| 选项 | 允许一次 / 拒绝 / 拒绝并说明原因（原因返回给模型） |
| 是否提供“始终允许” | 首版不提供（见 D4）。需要长期允许的目录，用 `/add-dir` 把它纳入项目 |
| 绑定 | 复用 `NativePolicyInvocation`：绑定原工具、原参数指纹、调用 ID、会话、权限代次，执行前复核，参数被替换即作废 |
| 展示内容 | 工具名、cwd、完整命令或参数、规范化后的目标列表，并逐项标出“项目外”或“目标无法确定”；批量调用一次展示全部项目外条目 |
| 拒绝 | 记住未改变的同一请求（现有 `denied` 集合与 `native-permission-denial-v1` 记录） |
| 超时 / Esc 取消 | 本次不执行，**不记为拒绝**；同一请求稍后可再次询问（修 R2） |
| 敏感路径删除被拦截（D3、D6） | 操作不执行。工具结果明确告知模型具体目标及禁止原因；用户界面同时明确显示被禁止的操作、目标和原因，不能只报含糊的执行失败 |
| 工作区外已有文件的覆盖或编辑（D5） | 操作不执行，立即暂停当前整轮任务并告知用户，等待下一步指令；不能只返回一个工具错误后继续后续步骤。普通工作区外删除仍询问，agent 目录修改按 D6 询问 |
| 无 UI（print、无 UI 的 RPC）、`approval: "never"` | 返回 `APPROVAL_REQUIRED`，不执行，不记为拒绝（现有行为） |
| Plan 模式 | 已拒绝已识别的原生命令与变更，不变；未知 MCP/第三方工具不在此保证内 |
| 子代理 | 缺少 UI 的子调用遇到需要批准的操作应停止并返回父会话；父会话外部写权限委派本身也必须纳入边界，不能用“重新分配 cwd”代替用户授权（N3） |
| 显式规则优先级 | 显式 `deny` 仍优先；显式 `allow` 规则**不能**覆盖 C/D/E（与 Claude Code “allow 规则不能批准 critical path”一致），否则宽泛的 `bash` allow 会让需求失效 |

### 实现位置

- 放在原生 `SessionExecutionPolicy.authorize()` 里，只有一个授权 owner（权限简化方案第 79 行：“同一次调用只有一个授权决策 owner”）。**不恢复**旧 resource-lifecycle-guard 扩展，避免双重审批。
- 原生 `delete`、`move`、`file_batch`：复用规范化目标（`paths()`），按实际操作区分普通工作区外删除的询问、受保护删除的拒绝以及 D5 的覆盖/编辑暂停。批量调用须在任何变更执行前完成整批判定，不能逐项执行到越界项才停止。
- D5 需要调用方配合暂停当前整轮任务；仅在 `authorize()` 抛出普通工具错误不足以满足要求。文件工具、`lsp_fix(write: true)` 及可识别的 shell 覆盖/编辑采用相同边界，D6 的 agent 目录修改询问规则优先。显式 `deny` 与受保护路径拒绝仍先于询问。
- `bash`、`powershell`：复用现有删除识别器，把它从扩展迁到 coding-agent core：
  - 入口 `packages/extensions/resource-lifecycle-guard/permission-bash.ts:811` `inspectBashPermissionScope()`，输出 `destructiveTargets`、`moveDestinations`、`unverifiableMutation`、`dynamicScope`。
  - PowerShell 入口 `permission-powershell.ts:4`，先走同一 Bash 识别再修正。
  - **复核更正**：`permission-bash.ts:25` 已包含 `del`/`erase`/`rm`/`rmdir`/`rd`，不是全部尚未识别。但 permission scope 与 `core.ts` 的 high-risk scan 是两层不同输出，不能互换覆盖声明。
  - 17 个探针确认：`del D:/outside/x` 能提取删除目标；`cmd /c del ...`、`cmd /c rd ...` 没有产出实际删除目标；`Remove-Item` 在 permission scope 中未标为 mutation，high-risk scan 虽识别删除，却把常见未加引号的 `D:\outside\x` 错解析为当前目录下 `outsidex`。`Set-Location` 后的相对删除也未正确跟踪。详见 N2。
  - `git clean`/`reset --hard` 的 high-risk 输出为 `workspaceWide`，不是具体文件列表；permission scope 中的 `.git` 是合成范围，不能直接当作实际删除 `.git`。Python 内联 `rmtree` 在 high-risk scan 有目标，但 permission scope 没有 mutation 标记。
  - 常见 PowerShell 别名、`.NET Delete`、`robocopy /MIR` 等仍需补齐。迁移必须按 Bash/PowerShell/cmd 各自语义产出统一的删除、覆盖、移动源/目标与不确定状态；不透明脚本保持 F 类边界。
- 只在宿主机模式下对 shell 调用运行分析；单次分析已有 128 项 / 512 KiB 上限（`shell-analysis.ts:4-5`）。不能据此把完整授权链排除在热路径契约之外；D5 的整轮暂停会涉及调度、事件交付等路径，实施时需按 `docs/performance/hot-path-allocation-contract.md` 审计完整生产调用链。

### 威胁模型与停止规则

本方案的范围是**防止模型误删**，不是对抗性安全边界；本轮用户已确认的具体行为以 2.6 为准。

- 只修：(a) 模型正常写法漏识别；(b) 正常命令被误拦。
- 转义、Unicode、字符串拼接、别名、`eval`、base64 解码、描述符路径等绕过写法，记录到边界清单（#161）而不扩展解析器。
- 真正的隔离是前两档的 Windows Sandbox。宿主机模式本来就是受信任执行。

## 2.5 明确不覆盖的边界

1. 不透明脚本或程序内部的删除（F 类）。
2. MCP 工具与第三方扩展工具：看不到参数语义。D9 的注解强制询问已明确暂缓，本轮维持现有授权规则。
3. cwd 跟踪存在语言差异：本轮 `cd D:/outside; rm -rf x` 解析出外部目标，同时保留不确定标记；`Set-Location ...; Remove-Item x` 未正确跟踪。不能沿用原 cwd 静默判作项目内，应按 E 类处理。
4. 删除链接本身与经链接删除目标必须区分。**当前原生 delete/move 不支持链接本身**（`capturePathIdentity()` 直接拒绝），不能写成当前已允许；shell 只有证明是删除链接本身时才可按该语义分类。通过链接访问目标时必须用规范化后的目标匹配全部工作区及保护根，当前有 N1 漏洞，不能声称已经完整覆盖。
5. 覆盖写（`>`、`Set-Content`、`Copy-Item -Force`）不算删除，但对工作区外已有文件的覆盖或编辑已按 D5 纳入“暂停并通知”。原生工具和能识别的 shell 写法应保持一致；不透明程序内部操作仍受第 1 条边界限制。

# 三、其他审计发现

## R2 授权对话框超时或取消被记为持续拒绝（取消链已复现）

- `execution-policy.ts:266-272`：`ctx.ui.confirm(..., { timeout: 60000 })`，返回 false 即写入 `denied` 集合和 `native-permission-denial-v1` 会话记录，并报 “User declined this operation”。
- `interactive-mode.ts:3151`：确认框只有 Yes/No，`result === "Yes"` 之外一律为 false。
- `extension-selector.ts:74-83`：倒计时结束调用 `onCancelCallback`，结果为 undefined，即 false。
- 后果：用户离开 60 秒或按 Esc，同一请求在本会话内永久被拒，之后同意也无法执行。旧 guard 的对话框没有自动超时。
- 修法：区分“明确拒绝”“取消”“超时”；只有明确拒绝才写入 `denied`。可考虑去掉 60 秒超时，或延长并像 Claude Code 那样只拒绝本次。
- 本轮提取生产 `showExtensionConfirm()` 方法体，用 selector 返回 undefined 模拟取消，再接真实 `SessionExecutionPolicy`：首次报 `User declined`，第二次相同请求报 `Explicitly denied`，弹窗计数 1、持久拒绝记录 1。未实际等待 60 秒；超时通过相同取消回调的源码确认。历史记录恢复问题见 N5。

## B1 `/add-dir` 大小写或短名导致沙箱全部失败（已复现）

- `/add-dir` 和 `sessionDirectories()` 使用 `fs.realpathSync`（JS 实现），它保留用户输入的大小写和 8.3 短名：`interactive-mode.ts:2950`、`session-execution-profile.ts:23`。
- 沙箱启动时用 `fs.promises.realpath`（native）规范化后严格比较：`workspace-backend.ts:157` `need(canonical === directory ...)`。
- 复现：任务临时目录中输入小写的 `extra`，磁盘为 `Extra`，得到 `{"stored":"d:\\...\\extra","native":"D:\\...\\Extra","backendCheckPasses":false}`。实测 `realpathSync("C:\\Users\\ADMINI~1")` 也保持短名，native 返回 `C:\Users\Administrator`。
- 后果：每次沙箱调用报 `Additional workspace identity changed`；该目录已持久保存，会话一直失败直到手动移除。
- 同源问题：`/remove-dir` 用 `indexOf` 精确匹配（`interactive-mode.ts:2953`），大小写不同会报“该目录不在当前附加工作区中”。
- “主工作目录不受影响”只能描述原审计观察到的启动方式，不能推广到任意 SDK/恢复入口；本轮未把它作为普遍保证。
- 本轮在独占夹具复现：磁盘目录为 `Extra`，`sessionDirectories()` 接收 `extra` 后仍保存 `extra`；native 得到 `Extra`，后端比较为 false，移除时 `indexOf` 为 -1。短名行为沿用原审计证据，本轮未重新创建 8.3 别名或读取真实用户配置。
- 修法：统一入口规范化，并处理已有会话保存的旧拼写；不能只修新 `/add-dir`。不要仅靠放宽字符串比较来取消身份检查，应保留规范路径、目录身份和重解析点检查。

## B2 三层排除名单不一致（来宾与发布器夹具已复现）

| 层 | 排除或拒绝的名字 | 位置 |
| --- | --- | --- |
| 宿主快照捕获 | `.git`、`.sp`、`.artifacts`、`.codegraph`、`node_modules` | `workspace-backend.ts:29` |
| 来宾 worker 路径检查 | `.git`、`.sp`、`node_modules`（`catalog` 跳过 `node_modules` 目录） | `workspace-worker.mjs:54` |
| 宿主写回校验 | `.git`、`.sp` | `workspace-tools.ts:135` |

- 命令写了 `.artifacts/`、`.codegraph/`：宿主无基线，若同名文件已存在则 `Host target already exists`，此时前面的文件已发布，整批中途失败，VM 被丢弃。若不存在，则这些“不进沙箱”的目录会被写回宿主。
- 命令在工作区内产生 `.git`（`git init`、`git clone` 到子目录）：来宾 `local()` 报 `Protected workspace path`，退出码 0 的命令也在收集阶段判失败。
- 本轮复现：`.artifacts`/`.codegraph` 内容成为写回候选；`.git`/`.sp` 内出现文件后，模拟命令退出码为 0，收集仍失败。宿主发布器先成功写入普通文件，再遇到已有 `.artifacts/existing.txt` 冲突，报告已发布 1 个文件并丢弃快照；已有冲突文件保持原内容。没有启动 VM，使用的是生产来宾入口与发布器。
- 修法需要共用**分类策略**，不能机械地共用一个排除集合：区分禁止工具访问的元数据、允许 VM 内使用但不写回的依赖/产物、初始快照是否导入、发布器拒绝的候选。D8 的 VM 私有目录不应因此变成来宾命令不可用。

## B3 宿主机模式可写 agent 目录（代码核实）

- `protected-path-policy.ts:4` 只保护工作区内 `.git`、`.sp`。
- 在 agent 目录位于普通工作区外、未命中其他 deny 规则时，`~/.sp/agent/config/settings.json`（`sandboxNetwork`、`executionPermissions`）和 `~/.sp/agent/session-execution/*.json`（会话权限记录）没有 agent 目录专属保护。现有文件覆盖仍要求有效读快照；“可写”不是无视其他写入前置条件。

## P1 后端执行失败统一请求丢弃 VM（源码与后端夹具核实）

- `workspace-backend.ts:222`：`run()` 的 catch 对所有错误调用 `discardSnapshot()`，包括：
  - 读不存在的文件、不支持的二进制或超过 2 MiB 的文本；支持的图片另有 16 MiB 上限，不能概括成所有二进制/所有超过 2 MiB 的文件；
  - snapshot 过期、edit 定位不唯一；
  - grep 空模式；
  - 命令退出码非 0（`workspace-worker.mjs:282`）；
  - 主机侧路径校验失败（发生在 VM 启动之前）。
- 本轮确认后端在业务调用失败后会请求 discard。授权阶段提前拒绝、`invoke()` 的 busy/closed 拒绝不属于 `run()` 的 catch，不能说任何层的所有错误都会销毁。清理失败会保留物理 owner 并关闭后续准入，不能声称 VM 已成功销毁。

  - csc 编译 `command.cs`；
  - 启动 VM；
  - 沙箱读写模式下，VM 内已安装的 `node_modules` 丢失。
- 文档（`execution-environments.md`）明确写了“失败后清理旧 VM 和快照”，是设计选择；见 D7。
- D7 已确认仅复用可证明无副作用的失败；本轮夹具还确认非零退出前生成的文件会留在来宾工作树中，而失败回复不返回 changes。若把这类失败也直接复用，下一次增量基线可能吸收残留修改，不能顺手扩大 D7。

## P3 构建产物超限（代码核实）

## 4.2 新发现与方案遗漏

### N1 附加工作区保护可被路径别名绕过（已复现，高）

- `execution-policy.ts:140-150` 先按原始 absolute 路径选择工作区，再解析真实路径。项目内 junction 指向附加工作区时，先选中了主工作区；真实目标在外部，只产生可被 host-write 放过的 `workspace_escape`，没有套用附加工作区 `.git/.sp` 保护。
- 对照：直接删除 `Extra/.git/config` 被拒；通过 `Main/extra-alias/.git/config` 则获准。真实 `SessionFiles → FileService → executeNativePlan` 链也成功删除了该**任务夹具文件**，不是只检查一个 helper 的返回值；owner pending 最终为 0。`.sp` 同类目标的授权遗漏也已复现。
- 修正要求：先规范化根与目标，再按全部工作区的真实身份及保护根判断。不能只在解析前选一个根，或把所有 `workspace_escape` 统一问一次后放行。

### N2 旧 shell 分析器不能直接等同于完整删除识别（已复现，高）

- `inspectPowerShellPermissionScope()` 先复用 Bash scope，而 high-risk scan 虽带 shell 参数仍存在路径语义差异。`Remove-Item -Recurse -Force D:\outside\x` 在 scope 层没有 mutation 标记，在 PowerShell high-risk 层将目标解析为 `Main/outsidex`，且没有标记目标不确定。
- `del D:/outside/x` 正确；`del D:\outside\x` 错当为项目内目标。`cmd /c del`、`cmd /c rd` 没有给出真实删除目标；`Set-Location` 没有正确更新后续删除 cwd。均是常见正常写法，不是刻意混淆绕过。
- `git clean/reset` 的 workspace-wide 语义、内联 Python/Node 的 high-risk 语义，需要与 permission scope 汇总；不能只读取 `destructiveTargets`，也不能把所有 opaque 程序一律按删除处理。
- 本项是**现有分析器缺陷及迁移方案缺口**；宿主原生模式目前本就不调用它，不能表述为“新检查已经被绕过”。

### N3 子代理分配目录不等于用户批准的工作区（授权与过滤器已复现，高）

- `native-delegation.ts:31-52` 对任意有效 `task.cwd` 构造 grant；host-write 未命中规则时默认允许。探针给出父工作区外的 `Outside`，得到 `writable: true`、`source: full-access-exact`，没有询问。
- child-guard 的文件工具只检查是否在**分配的 cwd**，无法阻止这种外部权限委派。`effectiveTools()` 的白名单确实排除 delete/move/file_batch，但仍可给允许变更的代理提供 write/edit。
- 用户定义且获准 Bash 的代理还有直接漏检：`child-security.ts:334`/`regex.ts:12` 拒绝 `rm -rf /outside/x`，却不拒绝 `rm -rf D:/outside/x`；内联 Python 删除也不在该过滤器的保证范围。本轮只调用过滤函数，没有启动子代理或执行这些命令。
- 子进程以 print/no-session 启动，参数未传父权限模式（`subagent/index.ts:1072-1085`）；`main.ts:774-778` 不对这种调用自动恢复父交互会话权限。因此还必须验证子进程实际生效的执行环境，不能仅凭父 host-write 或 child-guard 推断整条链已隔离。
- 实施 D5/D6 时同时约束父级委派的外部写能力；模型给子代理指定 cwd 不等于用户执行 `/add-dir`。

### N4 D5 的立即暂停需要调度级控制（生产函数夹具已复现，高）

- `agent-loop.ts:921-925` 将授权抛错转为普通工具失败；顺序循环继续后续调用。`shouldTerminateToolBatch()`（807）还要求本批**所有**结果都 terminate，顺序循环只在 signal aborted 时提前中止。
- 提取生产顺序调度函数及其终止判定，首调用返回 block/terminate 对应结果，第二个执行回调仍运行一次，最终 `batchTerminate=false`。因此仅新增错误码、提示文本或单次 terminate 都不满足用户要求。
- 需要覆盖顺序批次、并行已接纳调用、CodeMode 嵌套调用与存量后台任务；定义停止新调用、取消/排空在途工作、保留已发生副作用的回执及明确用户通知。涉及调度、事件交付时必须遵守热路径分配契约。

### N5 旧拒绝记录与修复后的恢复路径（代码核实，中）

- `native-permission-denial-v1` 只保存 key，不保存明确拒绝、取消、超时的来源；恢复 owner 会重新加载它。修复新对话框不会自动修复已存在的误拒。
- 不能猜测并清空所有记录，否则会同时抹掉真实用户拒绝。实施需给出明确、用户可见的撤销/重新授权或会话迁移方案，并验证批量请求与其单项拒绝的关系。

### N6 范围内搜索受范围外内容影响（来宾入口夹具已复现，中）

- `workspace-worker.mjs:248` 先 `catalog(root)` 扫描全工作区，再以 `matchesScope()` 过滤。夹具中 `safe/ok.txt` 完全正常，只因范围外 `.git/config` 存在，`ls {path:'safe'}` 仍报 `Protected workspace path`。
- 与 B2 的元数据收集策略一起修正；范围外重解析点、全树容量等也不能被误认为目标范围内的业务错误。D7 保留 VM 后尤其不能留下所有后续范围搜索持续失败的状态。

其他实施约束：D8 必须区分初始导入与写回；D6 必须使用实际 agentDir；批量询问需要展示操作类型及移动的源/目标，当前仅 `paths.join('\n')` 不足。以上是需求落实所需的边界补充，不表示已改代码。

## 5.1 子代理问题

### S1 长任务完成后因 `agent_end` 超限被判失败（生产函数夹具已复现，高）

- 子进程以 `--mode json` 运行，`print-mode.ts:138-140` 把每个会话事件原样写到 stdout；`json-event.ts` 只去掉 `message_update` 的累积快照。
- 普通未改写工具结果在流中至少出现 **5 次**：`tool_execution_end.result`（`agent-loop.ts:1412-1415`）、`message_start.message`（1439）、`message_end.message`（1440）、`turn_end.toolResults`、`agent_end.messages`（后者为这次 agent loop 的新增消息）。原文漏掉 `message_start`。`AgentSession` 会转发此事件，`toJsonEvent()` 不删去其结果内容；生产事件构造函数夹具已确认这 5 份，实际消息还可能附带其他内容。
- 父进程对每一行都执行 8 MiB 单行上限（`subagent/index.ts:918-929`），超限即设置错误并杀掉进程树。父进程实际只使用 `message_end`。
- 夹具：用生产 `toJsonEvent()` 生成 `agent_end` 行，再交给生产 `jsonEventLimitReason()` 判定。每次读取为默认上限 50 KiB：

  | 满额读取次数 | `agent_end` 行字节 | 结果 |

  | 100 | 5,148,003 | 通过 |
  | 160 | 8,236,983 | 通过 |
  | 162 | 8,339,949 | 通过 |
  | 163 | 8,391,432 | `Subagent JSON event exceeded 8 MiB.` |
  | 170 | 8,751,813 | `Subagent JSON event exceeded 8 MiB.` |
  | 200 | 10,296,303 | 同上 |

- 后果：正常完成的最后一个 `agent_end` 也可能被拒，父进程记录错误、请求结束进程树，最终返回优先显示该错误而非已收到的报告。本次直接调用生产 `processLine()`：162 次夹具接受、结束请求 0 次；163 次夹具拒绝、结束请求 1 次（结束函数为计数替身，没有真实子进程）。

### S2 子进程实际执行环境未与父会话绑定（源码及内存设置对象核实，未启动子进程，高）

- 子进程参数（`subagent/index.ts:1072-1086`）不含 `--execution-environment` 或权限模式。`main.ts:777` 仅在 interactive 模式或显式传入时设置权限模式，所以子进程权限模式为空。
- 子进程是否创建原生策略，取决于全局 `executionEnvironment`（`resource-loader.ts:608-611`）：
  - 未设置（较早的安装）：没有原生策略，只有 child-guard。
  - `trusted-host`：未配置额外显式规则时，原生策略在模式为空时，`execution-policy.ts:178` 的默认结果只对 `read` 和 SAFE 工具为 allow，`grep`/`find`/`ls`/`write`/`edit`/`bash` 为 ask；子进程无 UI，变成 `APPROVAL_REQUIRED`。即默认工具集中只有 `read` 能用（完整子进程行为为推断，未运行）。
  - `sandbox`：Windows 首次安装时 `settings-manager.ts:435-438` 会写入此值。子进程在沙箱环境中启动，工具走 VM 后端，并同样遇到上一条的 ask 规则；父会话是宿主机模式，子进程却可能尝试启动自己的 VM（推断，未运行）。
- 现有子代理测试（`tests/subagent-management.test.ts`）使用旧的 `workspace-write` grant，没有覆盖原生权限模式下子进程的实际环境。
- 结论：N3 最后一条“必须验证子进程实际生效的执行环境”成立，且三种全局配置会导致三种不同行为。建议父进程显式传入执行环境，并为子进程定义专门的权限档（D10），再补一个启动真实子进程的 live 用例。
- 本轮用 `SettingsManager.inMemory()` 验证未设置、`trusted-host`、`sandbox` 三种设置：环境值各自保留，权限模式均为 undefined。再调用 `setExecutionEnvironmentForSession('trusted-host')` 也不设置权限模式。因此单加 CLI 环境参数不足以实现 D10；没有读取真实用户配置，尚未验证完整启动链。

### S3 运行中没有进度（代码核实，中，TUI）

- 只在启动和结束时各推送一次（`emitSingleResultUpdate`，`subagent/index.ts:1103/1142`）。启动时快照的用量为 0，所以最长 2 小时内状态一直是 `0 turns ↑0 ↓0 $0.0000`，也看不到当前工具。
- `SubagentStatusText.render()` 的注释（`subagent/index.ts:322`）写明：已用时间只在其他界面事件触发重绘时才前进。
- 修法：在 `message_end` 等完成边界更新进度（轮数、token、费用、最近工具名），再合并并节流发布；一轮可能有多个 `message_end`，不能把每个事件直接发布等同于“每轮一次”。运行期间可复用 `codemode-tree.ts` 的 1 秒 tick 方式刷新。改动涉及事件交付与渲染，属于热路径，需按分配契约审计。

### S4 stderr 收集与失败摘要均截取开头（生产函数夹具已复现，中）

- `onStderrData()` 用 `capText(stderr + chunk, 32 KiB)`，保留开头、丢弃之后的内容；`failureDisplayText()` 和 `getResultOutput()` 在没有 `errorMessage` 时显示 stderr。进程最后打印的错误会被截掉。
- 第二层丢失：`failureDisplayText()`（554-567）默认再用 `capText(..., 4096)` 截取开头；`runSingleAgent()`（1139-1140）把这个摘要存入 `errorMessage`，最终 `getResultOutput()` 优先使用它。因此只把收集改成 32 KiB 首尾保留，仍可能丢掉最终错误。
- 本轮探针：字符串 `prefix`、换行、64 KiB 点号、换行和 `FINAL_ERROR_MARKER`。现有收集器不保留标记；生产 `capTextHeadTail(..., 32 * 1024)` 保留标记，但接生产 `failureDisplayText()` 后标记再次丢失（输出 4,108 字节，含截断提示）。最终摘要也用首尾保留的候选格式时，输出 3,904 字节且保留标记；短错误对照正常。这只是候选格式验证，未改生产逻辑。
- 修法必须覆盖“收集 → 失败摘要 → 最终返回/界面”：约束各阶段字节预算，明确保留末尾错误及截断提示，避免 `errorMessage` 优先级再次遮蔽有用诊断。还需覆盖多 chunk、UTF-8 边界及已有 `errorMessage` 的组合，不仅替换 `onStderrData()`。

- 每个子代理都冷启动完整进程，运行时加载 `child-guard.ts` 并写临时提示词文件；启动耗时未测，建议优化前先测量。

## 5.2 子代理设计

- **S6 两档沙箱下不可用**。`subagent` 不是沙箱工具定义，`supports()` 为 false，工具被隐藏（`agent-session.ts:4951-5003`），直接调用返回 `SANDBOX_UNSUPPORTED`；`execution-environments.md:98` 已声明。默认的沙箱模式因此没有委派能力。可选方向（D11）：维持现状；或只开放只读子代理，子进程的工具改走父会话的沙箱后端（需要解决单 VM 并发与快照共享）。
- **外部写权限委派**：与 N3 是同一问题。子代理分配目录只限制其可访问范围，不能扩大“主目录 + 用户 `/add-dir`”组成的工作区，也不能通过一次目录委派询问授予绕过后续操作分类的权限。普通工作区外删除按 R1 询问；覆盖或编辑外部已有文件按 D5 不执行并暂停父会话整轮任务、告知用户；关键目标与 D3/D6 删除拒绝，agent 目录修改按 D6 询问。D5 不额外禁止普通外部新建文件，但也不等于无条件允许。缺少所需父级询问或暂停通道时，应在发生副作用前停止并返回父会话，不能静默降级。具体跨进程权限机制仍属 D10 待确认方案。
- **CodeMode 中调用**：`subagent` 为 `modelOnly`，代码注释说明原因是前台任务可达 2 小时而脚本最多 300 秒。后台启动会立即返回任务 ID，可以考虑仅对 `background: true` 放开；这是功能建议，未评估对任务所有权的影响。
